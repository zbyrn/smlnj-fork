• Yes, largely representation/calling-convention driven.

  pair vs fpair are treated differently because float pairs are carried as unboxed 64-bit data (RK_RAW64BLOCK) in later CPS/CFG, while ordinary pairs are normal boxed-ish tuple paths.

  Where that decision is made:

  1. Runtime type classification into pair/fpair

  - compiler/FLINT/reps/rttype.sml:311
  - TC_TUPLE [t1,t2] becomes tcode_fpair if both float-like, else tcode_pair.
  - Codes defined at compiler/FLINT/reps/rttype.sml:202.

  2. Arrow coercion dispatch on those codes

  - compiler/FLINT/reps/typeoper.sml:341
  - In tcCoerce, arrow case does isPair; when MAYBE, it emits runtime tests against tcode_pair/tcode_fpair and generates 3 adapters (pair, fpair, fallback cast): compiler/FLINT/reps/typeoper.sml:348, compiler/
    FLINT/reps/typeoper.sml:395, compiler/FLINT/reps/typeoper.sml:428.

  3. Backend has distinct raw-float record path

  - RK_RAW64BLOCK kind: compiler/CPS/cps/cps.sml:17
  - Construction/lowering uses that path: compiler/CPS/convert/convert.sml:93, compiler/CPS/convert/cpstrans.sml:115, compiler/CodeGen/cps-to-cfg/cps-to-cfg-fn.sml:213.

  If you don’t want this specialization:

  - There is no single existing runtime flag that disables pair/fpair specialization in reify.
  - Control.FLINT.sharewrap (compiler/FLINT/main/control.sml:113) only shares wrappers; it does not turn off pair/fpair logic.
  - Practical options:

  1. Preferred: keep specialization, but reduce blow-up by lifting/memoizing coercion wrappers (the comment already points here in typeoper.sml).
  2. Hard disable (experimental): patch tcCoerce arrow MAYBE case to always use fallback hh3 (or return NONE), and/or stop producing tcode_fpair in rtLexp. This can break correctness unless you also ensure no
     code expects specialized pair/fpair calling paths.

  If you want, I can draft a minimal “disable fpair only” patch first (lower risk than disabling both pair+fpair) so you can measure behavior.
